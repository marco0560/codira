## Root Cause

The remaining DuckDB slowdown is not because DuckDB is intrinsically slow. It is
because the plugin is still architected like a row-oriented transactional
backend with some bulk inserts grafted onto it.

The key anti-pattern is:

```text
for each analyzed file:
    persist_store_analysis(file)
    allocate ids with SELECT MAX(id) on first use per table
    build per-file module/class/function/documentation bookkeeping
later:
    bulk flush accumulated rows
```

That keeps too much of the write plan in Python and sends DuckDB thousands of
small persistence decisions and SELECTs before reaching the bulk-load parts.
DuckDB is strongest when given columnar relations and set-oriented SQL plans.
The current plugin uses Arrow and CSV in some flush paths, but the full index is
still organized around per-file mutation semantics.

The second important issue is duplication around embeddings/vector storage:

- `embeddings.flush_pending_rows` is materializing 66,510 rows per full matrix.
- `vector_store.store_vectors` is also materializing 66,510 rows.
- For DuckDB, this means a DuckDB structural backend plus a separate DuckDB
  vector-store path are both doing work. This is technically modular, but not
  native for a DuckDB-optimized full-index build.

The third issue is fixed overhead:

- 1,128 index creation calls across 24 profiles.
- 48 commits across 24 profiles.
- Fixed index/commit costs dominate small repositories.

The recent lifecycle fix helped, but it does not change the basic write model.
The full-index path is still not DuckDB-native.

## Salvage Decision

DuckDB is salvageable only if we stop iterating on the current persistence
shape.

Continuing to tune the current plugin incrementally is not worth it. The data
shows the bottleneck is architectural:

- per-file persistence remains the hottest path;
- vector persistence is duplicated across structural and vector-store layers;
- index/commit overhead is still large enough to dominate small repos;
- current bulk paths are partial, not end-to-end.

Recommendation:

- Do not spend more time on micro-optimizations of the current code path.
- Either build a DuckDB-native v2 write path with an explicit acceptance gate,
  or deprecate DuckDB as a production backend and keep SQLite as default.

The plugin is worth one final, radical salvage attempt if the goal is to keep a
DuckDB backend for analytical/vector-heavy future work. It is not worth further
incremental work if the only goal is to beat SQLite on current small-repo Codira
benchmarks.

## Resolutive Fix Plan

### 1. Add a DuckDB-native full-index builder

Implement a separate full-index path for DuckDB instead of routing full rebuilds
through the same per-file persistence method.

Design:

- Analyzer output is collected into in-memory columnar row buffers by table.
- IDs are assigned in one deterministic planning pass, not through per-file SQL
  lookups.
- All structural tables are loaded from Arrow or Parquet relations in table
  order.
- Derived relation tables are created with `CREATE TABLE AS SELECT` or
  `INSERT INTO ... SELECT`, not Python loops.
- Indexes are created only after all table loads finish.
- Full rebuild writes into a fresh DuckDB database or staging schema, then
  atomically swaps the result into place.

Target native constructs:

- `CREATE TABLE AS SELECT`
- `INSERT INTO ... SELECT FROM read_parquet(...)`
- Arrow relation registration only for large whole-table batches, not per-file
  operations
- `COPY`/Parquet staging for very large relation tables such as reference scan
  rows
- one transaction for structural load plus one final checkpoint/swap

Acceptance:

- DuckDB `index --full` median <= 1.15x SQLite on this 4-repo matrix.
- Small-repo fixed overhead no worse than 1.25x SQLite.
- No regression in `sym`, `calls`, `audit`, `ctx`, or `emb`.

### 2. Collapse DuckDB structural and vector writes for full index

For DuckDB backend plus DuckDB vector store, avoid treating the vector store as
a separate database write path during full-index builds.

Options:

- Preferred: one DuckDB file owns both structural and vector tables for DuckDB
  backend runs.
- Acceptable transitional path: pass the active DuckDB connection into the
  DuckDB vector store during indexing so vector writes share the same native
  session and staged transaction.

This removes the current double-DuckDB shape:

```text
structural DuckDB backend writes embeddings metadata
separate DuckDB vector store writes materialized vectors
```

Acceptance:

- `vector_store.store_vectors` is no longer a separate 0.5-1.2s median cost in
  DuckDB profile output.
- Full-index DuckDB profile shows vector rows loaded as part of the same
  whole-table load plan.

### 3. Remove per-file `persist.store_analysis` from full-index hot path

Keep `_store_analysis` only for incremental updates or compatibility tests.
Full rebuilds should not call it per file.

Implementation sketch:

- Add a full-index planning object that takes all `FileAnalysis` records.
- Build deterministic maps:
  - file path -> file id
  - module stable identity -> module id
  - class stable identity -> class id
  - function stable identity -> function id
- Emit final table row arrays directly.
- Resolve call/reference/documentation rows against those maps in memory.
- Flush each final table once.

Acceptance:

- DuckDB profile no longer has thousands of `persist.store_analysis` calls.
- `sql.select` call count during full index drops from about 5,082 across the
  matrix to near schema/index bookkeeping only.

### 4. Make index creation coarse-grained and measurable

Current profile shows 1,128 `sql.create_index` calls across the matrix. That
cost is real and fixed.

Actions:

- Review every DuckDB index for query evidence.
- Drop indexes that do not affect current `sym`, `calls`, `refs`, `audit`,
  `ctx`, `emb`, `symlist`, or `cov` commands.
- Prefer fewer composite indexes matching actual query predicates.
- Keep a dedicated test that asserts the index set is intentional, not just
  inherited from SQLite.

Acceptance:

- `prepare.create_schema_indexes` median falls below 0.25s on `codira` and
  `fontshow`.
- Query medians remain within 1.1x SQLite or improve.

### 5. Set a hard go/no-go gate

Run the same campaign after the rewrite:

```bash
uv run python -m scripts.run_final_embedding_model_campaign --runs 5 --warmup 1 --manifest benchmarks/embedding/uv-backed-repos.local.json --model-manifest benchmarks/embedding/model-candidates.json --backend both
```

Go criteria:

- `index --full`: DuckDB median <= 1.15x SQLite.
- incremental `index`: DuckDB median <= 1.10x SQLite.
- `ctx`, `emb`, `sym`, `calls`, `audit`: DuckDB median <= 1.15x SQLite.
- No memory spiral.
- DuckDB profile confirms no per-file persistence hotspot.

No-go criteria:

- If a DuckDB-native v2 full-index path still cannot get below 1.25x SQLite on
  full index, stop investing in DuckDB as a primary Codira backend.
- Keep DuckDB only as an experimental/analytical backend or remove it from the
  recommended first-party bundle.

## Non-Regression Tests

Required tests for the rewrite:

- Full-index DuckDB path does not call `_store_analysis` per file.
- Full-index DuckDB profile contains one table-load span per structural table.
- `codira.analyzers` remains absent from core imports.
- SQLite and DuckDB produce equivalent symbol, call, ref, audit, documentation,
  and embedding query results for a mixed Python/C/C++/Bash/Markdown fixture.
- DuckDB index metadata, runtime inventory, and embedding backend state match
  SQLite semantics.
- DuckDB vector rows are query-compatible with existing `emb` and `ctx`.
- Custom Semgrep rule prevents reintroducing DuckDB `executemany` and can be
  extended to flag per-row or per-file DuckDB persistence loops in full-index
  paths.

## Bottom Line

DuckDB is not currently competitive with SQLite for Codira full-index workloads:
median full index is still about 2.04x slower.

The plugin is salvageable only with a DuckDB-native full-index rewrite. The
current implementation has already received enough incremental tuning to show
its ceiling. If the v2 rewrite is not acceptable in scope, the pragmatic
decision is to stop trying to make DuckDB the default-quality backend and keep
SQLite as the production backend.
